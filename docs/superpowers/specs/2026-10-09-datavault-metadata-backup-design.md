# `.datavault` 元数据备份 / 恢复设计（已批准）

> 状态：**已批准**（用户确认）  
> 日期：2026-10-09  
> 范围：**仅设计文档**；本轮不改 Rust / Vue 业务代码  
> 相关：[备份盘受控文件设计](./2026-09-28-backup-disk-controlled-files-design.md)、盘根 `.datavault/`（`disk.json`、`vault.db`、批次元数据 JSON）

## 1. 背景

DataVault 将受控盘的关键元数据集中存放在盘符根目录的 `.datavault/` 下，主要包括：

- `disk.json`：受控盘标记（`is_backup_disk` / `app` 等）
- `vault.db`：受控文件清单（`controlled_files`）
- 可选：旁路批次元数据 `<批次ID>.json` 等同目录内文件

元数据损坏、误删、换机迁移或盘面重装时，若无独立备份，受控清单与校验指纹会丢失。用户需要一套**手动触发**的、可校验完整性的 `.datavault` 目录级备份与恢复能力。

## 2. 目标

1. 用户选择一台**已标记的受控盘**后，可将该盘根 `.datavault/` **整目录**导出为**单个 zip** 归档。
2. 导出文件名由用户**手动命名**：对话框提供**可编辑名称框**，**预填合理默认名**（例如带时间戳），用户可在保存前修改。
3. 用户可从 zip **恢复**到目标盘根的 `.datavault/`。
4. 恢复前校验归档完整性（见第 6 节：清单中的文件名 + 大小 + 哈希）。
5. 若目标盘已存在 `.datavault/`，恢复前**先备份现有目录**，再覆盖写入。
6. 本轮只交付设计文档；实现另开任务。

## 3. 非目标

- 本轮**不实现**任何 Rust / Vue 代码、命令或 UI 控件。
- **不做**自动定时导出、云同步、多盘清单合并。
- **不加密**归档内容（后续若需要再单独立项）。
- **不**把 `.datavault` 迁出盘根到应用数据目录；清单仍「随盘走」。
- **不**改变现有 `disk.json` / `vault.db` / `controlled_files` schema。
- **不**纳入 MSI / 安装包工作。
- 恢复**不**自动重建或校验盘上受控**数据文件**本身（仅恢复元数据目录）；数据文件完整性仍走既有完整/快速校验。

## 4. 导出

### 4.1 触发与前置

- **手动触发**：用户在 UI 中选择一台受控盘（盘符根已标记），再选择「导出 `.datavault` 元数据」。
- 前置条件：
  - 目标为已检测的受控盘（存在合规 `disk.json`，`is_backup_disk=true`，`app=DataVault`）。
  - 盘仍挂载且 `.datavault/` 可读。
- 非受控盘或不存在 `.datavault/` 时拒绝并提示。

### 4.2 归档格式

- 产出**单个 zip** 文件。
- 归档内包含该盘 `.datavault/` 下的全部常规文件（至少 `disk.json`、`vault.db`；若有批次元数据 JSON 等一并纳入）。
- 建议 zip 内路径以 `.datavault/` 为根前缀（例如 `.datavault/disk.json`），便于一眼识别内容且与盘上布局一致；实现阶段固定一种并与清单路径一致。
- 不在 zip 内嵌嵌套 zip；不压缩盘上其它用户数据文件。

### 4.3 文件命名（手动 + 预填默认）

- 导出对话框展示**可编辑的名称输入框**。
- **预填默认名称**（示例，实现可微调格式，但须可读且含时间信息）：
  - `DataVault-meta-<盘符>-YYYYMMDDHHmmss.zip`
  - 例：`DataVault-meta-E-20261009200500.zip`
- 用户可在保存前**随意修改**名称（仍须以 `.zip` 为扩展名或由保存对话框自动补全）。
- **禁止**仅系统静默用时间戳命名、不允许用户改名的流程；预填默认 ≠ 自动定稿。
- 保存位置：由系统「另存为」对话框让用户选择本地路径（可为其它盘、网络盘等）；与「导出源受控盘」解耦。

### 4.4 导出时写入清单（manifest）

导出 zip 时同步生成并写入归档内的 **manifest**（建议文件名：`.datavault/manifest.json` 或归档根 `manifest.json`；实现时二选一并文档化），用于恢复前校验。清单至少包含：

| 字段 | 说明 |
|------|------|
| `format_version` | 清单格式版本，初始 `1` |
| `app` | 固定 `"DataVault"` |
| `exported_at` | ISO-8601 带时区 |
| `source_drive` | 导出时的盘符标识（如 `E:`），仅供展示 |
| `entries[]` | 每个被打包文件一项 |

每个 `entries[]` 项：

| 字段 | 说明 |
|------|------|
| `path` | 归档内相对路径（与 zip 条目一致） |
| `size` | 字节大小 |
| `hash` | 文件内容哈希（建议 SHA-256，小写 hex；实现选定后不得无文档变更） |
| `hash_alg` | 如 `"sha256"`（可放在顶层一次声明） |

- 清单自身**不**列入 `entries` 的自哈希循环；或采用「先写临时清单再封包」的固定顺序，实现时写清。
- 导出过程应可取消；大 `vault.db` 时在状态面板显示进度（实现阶段对齐现有 Job 模型）。

### 4.5 建议命令（实现指引，非本轮代码）

| 命令（名称可微调） | 作用 |
|--------------------|------|
| `export_datavault_metadata` | 指定盘符 + 目标 zip 路径；打包 `.datavault` + 写 manifest |

## 5. 恢复

### 5.1 触发与前置

- 用户选择目标盘（通常为盘符根），选择「从 zip 恢复 `.datavault`」。
- 选择本地 zip 文件。
- 目标盘须可写；建议要求目标为盘符根（与「标记为受控」一致），避免写到子目录。

### 5.2 流程（顺序固定）

1. **打开并解析 zip**，定位 manifest。
2. **完整性校验**（第 6 节）：任一失败则**中止**，不改动盘上现有 `.datavault/`。
3. **语义校验**（建议）：解压预览或从 zip 读取 `disk.json`，确认 `app=DataVault` 且 `is_backup_disk=true`；否则拒绝并提示「非 DataVault 元数据归档」。
4. **若目标已存在 `.datavault/`**：先将其**整目录备份**到安全位置，再覆盖。
   - 备份位置建议（实现择一并写清）：
     - 同盘根旁路：`.datavault.bak-<YYYYMMDDHHmmss>/`，或
     - 用户可选目录 / 自动放到应用临时区后再提示路径。
   - 备份失败则**中止恢复**，不覆盖原目录。
5. **原子性尽量接近**：先解压到临时目录（同盘或系统临时区），校验通过后再替换/重命名到盘根 `.datavault/`；失败则保留原备份、清理临时产物并报错。
6. 成功后刷新受控盘检测与浏览列表。

### 5.3 覆盖策略

- 恢复结果是用归档内容**替换**目标盘根 `.datavault/`（不是与旧库做行级合并）。
- 不在本设计中做 `controlled_files` 与盘上文件的自动差量合并。

### 5.4 建议命令（实现指引）

| 命令（名称可微调） | 作用 |
|--------------------|------|
| `verify_datavault_backup_zip` | 仅校验 zip + manifest，不写入 |
| `restore_datavault_metadata` | 校验 → 备份现有 → 恢复到盘根 `.datavault` |

## 6. 校验

恢复（及可选的「仅校验」入口）必须验证：

1. **zip 可读**：能完整打开，无截断/损坏。
2. **manifest 存在且可解析**：`format_version` 受支持；`app=DataVault`。
3. **条目一致性**（对 `entries[]` 中每一项）：
   - zip 内存在对应 `path`；
   - 实际大小 = `size`；
   - 按声明算法重算哈希 = `hash`。
4. **多余/缺失**：
   - manifest 有而 zip 无 → 失败；
   - zip 内有未列入 manifest 的业务文件（除约定的 manifest 本身）→ **失败**（严格模式，避免被塞入未知文件）。
5. 校验失败：**不写盘**；UI 展示失败原因（缺文件 / 大小不符 / 哈希不符 / 清单无效）。

说明：此处「哈希」指归档内**元数据文件**的完整性指纹，与受控数据文件的 MD5 / FastMD5 无关。

## 7. UI

### 7.1 入口位置（实现阶段对齐现有主窗）

- 建议放在主窗口侧栏「受控 / 备份」相关区域，或受控盘上下文操作：
  - **导出元数据…**
  - **恢复元数据…**
  - （可选）**校验元数据备份…**（只校验不写入）
- 仅在选中/当前为受控盘符根时启用「导出」；「恢复」在选定可写盘符根后启用。
- 长任务走下方**状态面板**（中文标签，如「导出元数据」「恢复元数据」），可取消。

### 7.2 导出对话框

1. 确认源受控盘（只读展示盘符）。
2. **名称编辑框**：预填默认名（含时间戳等），**可改**。
3. 「浏览…」选择保存目录或直接「另存为」选定完整路径（名称与路径可合并进系统保存对话框，但须保证用户能改文件名）。
4. 确认后开始导出；完成后提示完整路径。

### 7.3 恢复对话框

1. 选择 zip 文件。
2. 选择目标盘符根。
3. 明确警示：将覆盖目标 `.datavault/`；若已存在会先自动备份原目录。
4. 可选：恢复前先跑「仅校验」并展示摘要（文件数、清单时间、源盘符）。
5. 用户确认后执行恢复。

### 7.4 文案

- 产品文案优先中文：「导出元数据」「恢复元数据」「元数据备份」。
- Tooltip（`title`）说明：导出的是 `.datavault` 清单与标记，**不是**盘上用户数据文件的拷贝。

## 8. 错误处理

| 场景 | 行为 |
|------|------|
| 源盘非受控 / 无 `.datavault` | 拒绝导出，提示先标记为受控 |
| 源盘拔出 / 无读权限 | 失败，状态面板显示错误 |
| 目标路径无写权限 / 磁盘满 | 导出失败，不留下半截有效「已完成」状态；清理不完整临时文件 |
| zip 损坏 / manifest 缺失 | 恢复前校验失败，不改动现有 `.datavault` |
| 大小或哈希不符 | 同上，列出首个或汇总失败项 |
| `disk.json` 的 `app` 不匹配 | 拒绝恢复 |
| 已存在 `.datavault` 且备份旧目录失败 | 中止恢复，保留原目录 |
| 恢复中途失败 | 尽量回滚到恢复前状态（保留 `.datavault.bak-*`）；提示备份路径便于人工挽回 |
| 用户取消 Job | 停止写入；清理临时目录；原 `.datavault` 保持不变（若尚未替换） |

## 9. 验收

实现阶段完成后，至少满足：

1. **文档**：本规格已合入；开发计划中有指向本规格的后续项。
2. **导出**：
   - 仅受控盘可导出；产出单个 zip；
   - 对话框名称框**预填默认名且可编辑**；用户改名后文件名与之一致；
   - zip 内含 manifest，且 `entries` 覆盖除清单约定外的全部打包文件。
3. **校验**：故意篡改 zip 内某文件字节后，恢复/校验报哈希失败且不写盘；删掉 zip 内某清单所列文件后报缺失。
4. **恢复**：
   - 空目标盘：恢复后出现合规 `.datavault/`，应用能识别为受控盘且 `vault.db` 可读；
   - 已有 `.datavault/`：先产生备份副本，再被归档内容替换；备份目录可找回覆盖前文件。
5. **非目标未做**：无自动定时导出；无业务数据文件打进该 zip；本设计提交不含 Rust/Vue 实现亦可先验收文档本身。
