# 优化方向

记录日期：2026-09-30。依据当时工作区源码的静态阅读（`src-tauri/src` 的 `hashutil.rs`、`vault.rs`、`job.rs`、`lib.rs`、`tarutil.rs`，以及 `src/main.ts` 的窗口入口）。未做运行计时。第一批、第二批、第三批已落地。

场景按移动硬盘上的建索引、备份、校验来估影响。时间主要花在读盘和逐条落库。完整 MD5 对 USB 盘通常是 IO 受限。

## 保持不动

- 发布配置已经是 LTO、`opt-level 3`、`strip`。
- 建立备份索引会跳过 `vault.db` 里已有的相对路径，不重复算哈希。
- 已写入 `vault.db` 的校验值继续用 MD5 / FastMD5，不更换算法。
- 同一块机械盘不要并行读。并行读会让磁头来回寻道，索引和校验更慢。
- 移动盘上的 `vault.db` 不要开 WAL。异常拔盘会留下 `-wal` / `-shm`，下次打开可能对不上。整批写入用一条连接上的 `BEGIN…COMMIT`。

## 建议顺序

1. 第一批（已落地）：单次读盘同时算出两种哈希、整批一个 SQLite 事务、tar 改为流式写入、受控归档的完整 MD5 与 FastMD5 只算一遍。批次快速校验仍额外读头尾 64 KiB 的旧版快速哈希，写入 `md5_quick`，避免和已有批次校验对不上。
2. 第二批（已落地）：目录只查 `rel_path`，文件用 HashSet、目录用排序前缀二分；每个盘的数量列只加载一次路径并在内存里按前缀计数，盘根计入全部受控文件。非 tar 复制边写边算旧版头尾 64 KiB 快速哈希，进度带上真实文件数。进度最多约每 200 ms 一条，最后一条和失败仍发出。受控校验的进度回调返回 false 时，在哈希该文件之前停。目录表和校验明细超过 200 行只挂载可见行。
3. 第三批（已落地）：任务 ID 加毫秒与递增序号；tar 受控判断改为单行 `SELECT 1`；删除未挂载的 `App.vue` / `VerifyApp.vue`。

## 第一批：建索引与打包

| 方向 | 位置 | 现状 | 改法 |
|------|------|------|------|
| 一次读盘算出两种哈希 | `vault.rs` `upsert_controlled_file` | 每个新受控文件先跑完整 MD5，再跑 FastMD5。10 GB 文件大约读 11 GB，后一次按 100 MB 做 seek | 一次顺序读：全程更新完整 MD5，每块前 10% 再更新 FastMD5 |
| 整批一个 SQLite 事务 | `vault.rs` `open_db` / `ensure_db`；`job.rs` 哈希循环 | 每登记一个文件都读 `disk.json`、打开库并执行建表、再打开一次、单条 `INSERT`。默认同步会在移动盘上逐条 fsync。小文件很多时，写库比算哈希更慢 | 任务开始时确认一次受控盘，复用一条连接，整批 `BEGIN…COMMIT` |
| tar 按流写入 | `tarutil.rs` `pack_files` | `read_to_end` 后再 `append_data`。单个数 GB 文件会把进程内存顶满 | `append_data` 直接接受文件 `Read`，不要先收成 `Vec` |
| 受控归档只哈希一遍 | `lib.rs` `backup_paths_inner` 打包分支 | 写完 `{批次ID}.tar` 后先算完整 MD5 写入批次元数据，随后 `upsert_controlled_file` 又算一遍完整 MD5 和一遍 FastMD5 | 对归档只做一次顺序读，同时得到完整 MD5 和 FastMD5，批次元数据与 `vault.db` 共用结果 |

顺带：`hashutil.rs` `compute_md5_full` 的读缓冲只有 64 KiB。顺序读改成约 1 MiB 的复用缓冲。FastMD5 的采样窗口按固定块读取，避免一次分配约 10 MB。

## 第二批：浏览与反馈

| 方向 | 位置 | 现状 | 改法 |
|------|------|------|------|
| 列目录只取路径 | `lib.rs` `list_dir` | `list_controlled_files` 把 `md5`、`fast_md5` 等列全部读出，界面只用路径。每个目录项再对全部受控路径做前缀比较。`is_dir` 和 `metadata` 各多一次 stat | 只查询 `rel_path`。文件用 `HashSet`，目录用排序后的前缀二分。用 `DirEntry` 的 `file_type` |
| 数量列读一次表 | `lib.rs` `controlled_files_under` | 一屏几十个受控文件夹就会把整表读几十次，还把哈希列一起拉回来。总文件数另外用 `is_dir` 逐项 stat | 计数任务开始时加载一次路径列表，在内存里按前缀计数。遍历用 `file_type` |
| 复制时顺便算快速哈希 | `lib.rs` 非 tar 的复制循环 | `fs::copy` 之后对源再算一次头尾 64 KiB 的旧版快速哈希。进度事件里 `total` 固定为 0 | 自写复制循环，边写边更新快速哈希。收集完文件后再发进度，带上真实 `total` |
| 进度事件节流 | `job.rs`，以及校验与备份的 `emit` | 每个文件都向界面发一条进度。海量小文件时，事件序列化和 WebView 刷新变成主线程负担 | 最多约每 200 ms 一条，结束时再发最终一条 |
| 取消校验立刻停 | `lib.rs` `start_verify_controlled` | 回调里把 `stop` 设为 true，随后丢掉。大目录点取消后磁盘还会继续读到结束 | 进度回调能返回是否继续，循环里看到取消就停 |
| 大列表窗口化 | `MainApp.vue`、`BatchManageApp.vue`、`AdvancedBackupApp.vue` | 目录表和校验明细都是 `v-for` 全量 DOM。结果上万条时滚动和筛选会卡 | 只挂载可见行 |

## 第三批：边界与死代码（已落地）

| 方向 | 位置 | 现状 | 改法 |
|------|------|------|------|
| 任务 ID 避免同一秒碰撞 | `job.rs` `new_job_id` | ID 形如 `{kind}-YYYYMMDDHHmmss`。同一秒内两个相同 kind 的任务会得到同一个 ID，后一个覆盖 HashMap 里的取消标志 | ID 加上递增序号或毫秒 |
| 判断 tar 是否受控时按主键查一行 | `lib.rs` `is_controlled_tar_file` | 展开归档前为了核对一条 `rel_path`，把全部受控行加载进内存再线性查找 | `SELECT 1 FROM controlled_files WHERE rel_path = ?` |
| 删掉未挂载的界面 | `src/App.vue`、`src/windows/VerifyApp.vue` | `main.ts` 只挂载 `MainApp`、`BatchManageApp`、`AdvancedBackupApp`。`App.vue` 与现窗口重复，改一处容易漏另一处 | 确认无引用后删除 |

## 验收时看什么

- 冷备盘上对同一批新文件建索引：磁盘读取量接近「文件总大小」而不是「总大小 + FastMD5 采样」；大量小文件时 `vault.db` 只在事务结束时同步一次。
- 打包一个数 GB 的源文件：进程内存不随源文件大小线性涨到整文件。
- 目标是受控盘时，归档 tar 的完整 MD5 只计算一次。
- 浏览受控盘大目录时，不再为每一行加载整张受控表。
- 校验进行中点取消，后续文件不再读盘。
